# AGENTS.md — инструкции для ИИ-агентов в workaly

## Карта репозитория

Монорепозиторий платформы фриланс-заказов и вакансий. Два стека:

- Go 1.25+: `auth-service` (HTTP-грань, Gin), `job-service`, `task-service`,
  `chat-service`, `notifications-service`, общий `catalogkit`.
- Rust 1.96+: `user-service` (gRPC, Tonic), `payment-service` (заготовка).
- Контракты: `contracts/*.proto`; Go-код генерируется `make proto`,
  Rust — при сборке из того же источника.
- Инфраструктура: `compose.yaml`, `scripts/smoke.py` (сквозная проверка),
  `scripts/check-schema.sh` (пробы ограничений схемы), CI в `.github/workflows/ci.yaml`.

Подробное описание и состояние сервисов — `README.md`; границы сервисов —
`docs/architecture.md`.

## Порядок чтения перед задачей

1. `docs/roadmap.md` — этапы S0–S7 и раздел «Общее правило приёмки изменения».
2. Хвост `docs/progress.md` — что сделано, что не завершено, какое изменение
   следующее.
3. Документ текущего этапа (`docs/s1-identity.md`, `docs/s2-catalogs.md`,
   далее по ходу плана) — согласованные решения; их изменение требует записи
   причины в самом документе.

## Проверки

- Локально без контейнеров: `make test` (Go: `go test -race`, `go vet`,
  `gofmt`; Rust: `cargo fmt --check`, `cargo test --locked`,
  `cargo clippy --all-targets -- -D warnings`).
- Контракты: `make proto` — перегенерация не должна давать расхождений.
- Контейнерный стенд: `docker compose up --build -d`,
  `curl --fail http://127.0.0.1:8080/readyz`, `python3 scripts/smoke.py`;
  пробы схемы — `scripts/check-schema.sh`. Сценарии отказа БД — по
  `docs/development.md`.
- Детали и требования к инструментам — `docs/development.md`.

## Правила приёмки

Единственный источник истины — раздел «Общее правило приёмки изменения» в
`docs/roadmap.md`. Не дублировать его сюда. Изменение считается готовым только
при выполнении всех применимых пунктов оттуда.

## Инварианты и безопасность

- Публичный доступ к системе запрещён до закрытия ограничений, перечисленных
  в `docs/development.md` (раздел «Ограничения текущей реализации»).
- Миграции не редактируются задним числом; схема меняется новыми миграциями.
- Секреты (`JWT_SECRET`, `DATABASE_URL`, `.env`) не читать без необходимости,
  не логировать, не включать в ответы и коммиты.
- Поле `actor`/идентичность не принимается из клиентских тел; права проверяет
  сервис-владелец данных (`docs/s1-identity.md`, `docs/s2-catalogs.md`).
- Пустые сервисы не выдавать за протестированные реализации.

## Подтверждение результатов

Утверждение «проверки пройдены» допустимо только с фактическим выводом
команд: exit code и ключевые строки. «Код компилируется» не является
доказательством готовности. Выполненные проверки отделять от невыполненных.

## Git

- Коммиты — атомарные, в формате conventional commits (`feat(auth): …`,
  `test(scripts): …`), по образцу существующей истории.
- Атомарность: один коммит — один логически завершённый набор изменений.
  Связанные исходники и тесты одной функции коммить вместе; независимые
  исправления разделять; не создавать искусственные коммиты на каждый файл.
- Коммит создаётся автоматически после успешных проверок и вердикта
  `APPROVED` ревьюера. При `REQUEST_CHANGES` или упавших проверках затронутую
  логическую единицу не коммитить до исправления и повторной проверки.
- Перед каждым коммитом: просмотреть diff, прогнать необходимые проверки,
  проверить `git status`; добавлять в индекс только конкретные файлы текущей
  логической задачи. `git add .` и `git add -A` не использовать, если в рабочем
  каталоге могут быть посторонние изменения.
- Если изменения нельзя безопасно разделить или промежуточное состояние
  не будет проверено работоспособным — остановиться и объяснить причину,
  а не создавать фиктивные коммиты ради формальной атомарности.
- `git push` запрещён автоматически — только по явному запросу пользователя.
  Force push и переписывание истории запрещены всегда. `git reset`,
  `git clean`, удаление volume'ов и другие разрушительные операции — только
  по явному запросу пользователя.
- Посторонние пользовательские файлы и незакоммиченные изменения пользователя
  не включать в коммиты, не трогать и не отменять.
