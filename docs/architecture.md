# Архитектура Workaly

Статус: исходные границы и ограничения. Этот документ отличает целевую
архитектуру от уже реализованной; изменения границ требуют записи причины здесь.

## 1. Две самостоятельные предметные области

`job-service` владеет вакансиями, откликами кандидатов и их рассмотрением.
`task-service` владеет заказами, предложениями исполнителей, согласованными
условиями, сдачей и приёмкой. У них разные API, состояния и таблицы.
Общего «универсального объявления/отклика» между ними нет.

Общими являются идентичность, профили, коммуникации и инфраструктурные механизмы,
но не правила найма и выполнения заказа.

| Владелец | Данные и решения |
|---|---|
| Auth | Учётные данные, сессии, восстановление и отзыв доступа (целевая граница) |
| User | Профиль, настройки, видимость; позже организация и членство по отдельному решению |
| Job | Вакансии, отклики, история рассмотрения, право работодателя на изменение |
| Task | Заказы, отклики, исполнитель, версии условий, состояния выполнения |
| Chat | Диалоги, сообщения, участники, подтверждение сохранения |
| Notifications | Предпочтения каналов, попытки и результаты доставки |
| Payment | Финансовый журнал, операции провайдера, возвраты, выплаты и сверка |

Спор по заказу пока относится к Task; процедурная модерация и апелляции требуют
отдельного проектирования. Не создавать сервис на каждую таблицу.

**Технический долг:** текущий User хранит пароль и реализует Login/Register.
Это временная граница существующего кода, не целевая модель. До добавления
профильного API нужно определить и выполнить перенос credentials в Auth с
сохранением идентификаторов и безопасным завершением частичной регистрации.
Auth не должен вечно зависеть от доступности профиля для проверки пароля.

## 2. Владение данными

- Каждый сервис имеет собственные миграции и доступ только к своим данным.
- Один PostgreSQL-кластер допустим; раздельные базы/пользователи обязательны при
  появлении нескольких владельцев. Никаких межсервисных SQL JOIN и записей в чужие таблицы.
- Идентичность передаётся стабильным ID. Username изменяем и не является ключом авторизации.
- Критический переход состояния проверяется и фиксируется одной транзакцией
  владельца, с защитой от конкурентного обновления.
- Профиль — не источник прав на чужой заказ: права проверяет владелец ресурса.

## 3. Контракты и транспорт

- Клиенты обращаются к HTTP API через gateway; сервисы проверяют полномочия сами.
- gRPC применяется для внутренних запросов с непосредственным результатом.
- Контракты protobuf хранятся в `contracts/`; generated Go-код коммитится и
  проверяется генерацией в CI. Удалённые номера полей не используются повторно.
- Текущий пакет `user` сохраняет wire-совместимость прототипа; новые API
  версионируются. Добавление обязательного для клиента поля требует согласованного rollout.
- Асинхронные последствия публикуются событиями. Создание заказа не ждёт
  отправки email. При появлении событий необходимы outbox и идемпотентный потребитель.
- Kafka планируется как транспорт событий; топики, ключи порядка, retention и
  политика повторной обработки определяются вместе с первым потоком событий.

## 4. Задержки, сбои и повторы

Для каждого сквозного сценария до реализации определить бюджет p95/p99,
зависимости и ответ при недоступности каждой из них. Значения — из требований
и измерений, не обещания на основании пустого стенда.

- Передавать deadline и отмену; внутренний timeout не превышает оставшийся бюджет.
- Ограничивать соединения, параллелизм, тело запроса, стоимость хеширования и очереди.
- Не повторять неидемпотентные команды автоматически. Идемпотентность относится
  к бизнес-результату и сохраняется у владельца операции.
- Таймаут после записи означает неизвестный результат: нужен запрос состояния,
  а не сообщение «ничего не произошло» и слепой повтор.
- События допускают повторную доставку; порядок гарантируется только в явно
  выбранной области. Не обещать сквозную exactly-once обработку.
- Отставание потребителей, outbox и очередь ошибок наблюдаемы и имеют процедуру восстановления.
- Кэш и поисковая проекция не разрешают денежные и авторизационные операции.

## 5. Безопасность и эксплуатация

- Внешний HTTPS, защищённая межсервисная сеть и идентификация сервисов обязательны
  до публичного доступа. Plaintext gRPC текущего Compose допустим только локально.
- Секреты не находятся в образах, репозитории, токенах пользователя и логах.
- Cookie-аутентификация требует политики Origin/CSRF и согласованной frontend-топологии.
- Логи, метрики и трассы связываются ID запроса; пароль, токен и содержимое
  личной переписки не логируются. Аудит значимых действий — отдельная задача.
- Liveness не зависит от БД; readiness отражает способность обслужить запрос.
- Сервисы корректно завершаются, миграции совместимы с rolling deployment;
  backup проверяется восстановлением, а не наличием файла.
- Kubernetes, Redis и дополнительные проекции вводятся с конкретной задачей,
  владельцем сопровождения и измеримым критерием пользы.
