# Локальная разработка

## Контейнерный запуск

Требуются Docker + Compose либо rootless Podman + `podman-compose`, Python 3
для smoke-проверки и свободный локальный порт 8080.

```sh
cp .env.example .env
openssl rand -hex 32
# Скопировать результат в JWT_SECRET в .env.
docker compose up --build -d
docker compose logs -f
```

Для Podman все команды `docker compose` заменить на `podman-compose`.
База и gRPC не публикуются на хост; HTTP доступен только на `127.0.0.1`.
Пароль PostgreSQL в Compose намеренно локальный; это не production-конфигурация.
Изменяя `AUTH_PORT`, изменить также порт `PUBLIC_ORIGIN`.

```sh
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
python3 scripts/smoke.py
docker compose down
```

Smoke создаёт отдельный аккаунт при каждом запуске, не удаляет существующие данные
и не предназначен для production. Остановка Compose сохраняет named volume базы.
Не удалять volume для исправления ошибки миграции: сначала разобраться с причиной.

На отдельном локальном стенде можно проверить отказ и восстановление зависимости:

```sh
docker compose stop user-db
python3 scripts/smoke.py --expect-unavailable
docker compose start user-db
python3 scripts/smoke.py
```

## Проверка вручную

```sh
curl -i -H 'Content-Type: application/json' \
  -d '{"name":"Example","username":"example","password":"long-example-password"}' \
  http://127.0.0.1:8080/register
curl -i -H 'Content-Type: application/json' \
  -d '{"username":"example","password":"long-example-password"}' \
  http://127.0.0.1:8080/login
```

Успех — HTTP 200, JSON с `user_id` и HttpOnly cookie `token` на один час.
Повтор username — 409; неверные credentials — 401; неверный ввод — 400;
недоступность зависимости — 503; deadline — 504 с неизвестным результатом операции.
Увеличенный минимум пароля применяется только при регистрации; существующие
аккаунты с более коротким паролем по-прежнему могут войти.

## Конфигурация

| Переменная | Сервис | Значение / требование |
|---|---|---|
| `JWT_SECRET` | Auth | Обязательный случайный ключ, не менее 32 байт; не логировать |
| `COOKIE_SECURE` | Auth | По умолчанию `true`; `false` только для локального HTTP |
| `PUBLIC_ORIGIN` | Auth | Разрешённый browser Origin без пути; по умолчанию `http://127.0.0.1:8080` |
| `HTTP_ADDR` | Auth | По умолчанию `127.0.0.1:8080` |
| `USER_SERVICE_ADDR` | Auth | По умолчанию `127.0.0.1:50051` |
| `DATABASE_URL` | User | Обязательное подключение PostgreSQL; не логировать |
| `GRPC_ADDR` | User | По умолчанию `127.0.0.1:50051` |

User применяет встроенные миграции перед открытием gRPC. При добавлении
данных/реплик понадобится отдельная процедура развёртывания миграций; миграции
не редактируются задним числом. Существующая первая миграция сохранена.
Runtime-запросы SQLx параметризованы; сборка и unit-тесты не требуют БД.
В Compose для SQL настроен `statement_timeout=3000`; для ручного запуска
применить такой же лимит на уровне роли/подключения.

Auth `/healthz` проверяет HTTP-процесс. `/readyz` запрашивает стандартный gRPC
health API User, который обновляет статус на основе `SELECT 1` раз в секунду.
Поэтому обнаружение отказа БД не мгновенное. Процесс не перезапускается только
потому, что временно недоступна зависимость.

## Проверки без контейнеров

Требуются Go 1.25+, Rust 1.96+, `protoc`, C toolchain. Для генерации Go-контрактов
также нужны `curl` и `unzip`; закреплённые инструменты скачиваются в `.tools/`.

```sh
make proto
make test
```

`make proto` запускается из корня и использует единственный источник
`contracts/user.proto`. Rust генерирует код из того же файла при сборке.
Изменение расположения `.proto` меняет descriptor filename, но не имена RPC и
номера существующих полей. Добавленный `user_id` требует обновить User до Auth:
новый Auth намеренно не выдаёт токен при ответе старого User без идентификатора.

CI проверяет работающие сервисы, generated Go-код и контейнерную smoke-проверку.
Пустые сервисы не выдаются за протестированные реализации. Проверки совместимости
с предыдущим опубликованным контрактом появятся до первого внешнего потребителя.

## Ограничения текущей реализации

- Credentials всё ещё принадлежат User; перенос в Auth запланирован в S1.
- JWT пока не является отзывной сессией. Нет logout, восстановления, ротации
  ключей, защищённых ресурсных API и распределённого rate limit.
- JSON-only вход, проверка Origin/Fetch Metadata и SameSite Strict — защита
  текущих двух endpoint, не готовая политика CSRF для будущего frontend/API.
- Ограничены тело запроса, соединения и параллельное хеширование, но это не
  заменяет защиту от перебора и распределённых атак.
- gRPC plaintext, нет сервисной аутентификации, TLS, метрик и трассировки.
- Смена ключа инвалидирует все существующие JWT; совместимого rollout ключей пока нет.

Публичный доступ до закрытия этих пунктов запрещён. Следующий этап — S1 из
[плана](roadmap.md), а не добавление бизнес-API поверх незавершённой безопасности.
