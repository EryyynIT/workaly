# Локальная разработка

## Контейнерный запуск

Требуются Docker + Compose либо rootless Podman + `podman-compose`, Python 3
для smoke-проверки и свободный локальный порт 8080.

```sh
cp .env.example .env
openssl rand -hex 32
# Скопировать результат в JWT_SECRET в .env.
docker compose up --build -d
docker compose logs -f
```

Для Podman все команды `docker compose` заменить на `podman-compose`.
База и gRPC не публикуются на хост; HTTP доступен только на `127.0.0.1`.
Пароль PostgreSQL в Compose намеренно локальный; это не production-конфигурация.
Изменяя `AUTH_PORT`, изменить также порт `PUBLIC_ORIGIN`.

```sh
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:8080/readyz
python3 scripts/smoke.py
docker compose down
```

Smoke создаёт отдельный аккаунт при каждом запуске, не удаляет существующие данные
и не предназначен для production. Остановка Compose сохраняет named volume базы.
Не удалять volume для исправления ошибки миграции: сначала разобраться с причиной.

На отдельном локальном стенде можно проверить отказ и восстановление зависимостей.
Smoke в режиме `--expect-unavailable` рассчитан на отказ `auth-db` (его же
останавливает CI):

```sh
docker compose stop auth-db
python3 scripts/smoke.py --expect-unavailable
docker compose start auth-db
python3 scripts/smoke.py
```

Отказ `user-db` деградирует другое: вход работает, а публичный профиль и
доставка профилей отвечают 503.

```sh
docker compose stop user-db
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/users/019a2b7e-7c3a-7b1a-8f0e-1a2b3c4d5e6f
# 503
docker compose start user-db
```

## Проверка вручную

```sh
curl -i -H 'Content-Type: application/json' \
  -d '{"name":"Example","username":"example","email":"example@example.com","password":"long-example-password"}' \
  http://127.0.0.1:8080/register
curl -i -H 'Content-Type: application/json' \
  -d '{"email":"example@example.com","password":"long-example-password"}' \
  http://127.0.0.1:8080/login
curl -i http://127.0.0.1:8080/users/<user_id>
```

Публичный профиль читается без сессии: 200 с `user_id`, `name`, `username`;
неизвестный `user_id` — 404; не-UUID — 400; больше 60 запросов в минуту с
одного IP — 429. В ответе никогда нет email и данных учётной записи.

Успех — HTTP 200, JSON с `user_id` и HttpOnly cookie `token` на 15 минут.
Повтор username — 409; неверные credentials — 401; неверный ввод — 400;
недоступность зависимости — 503; deadline — 504 с неизвестным результатом операции.
Увеличенный минимум пароля применяется только при регистрации; существующие
аккаунты с более коротким паролем по-прежнему могут войти.

## Конфигурация

| Переменная | Сервис | Значение / требование |
|---|---|---|
| `JWT_SECRET` | Auth | Обязательный случайный ключ, не менее 32 байт; не логировать |
| `COOKIE_SECURE` | Auth | По умолчанию `true`; `false` только для локального HTTP |
| `PUBLIC_ORIGIN` | Auth | Разрешённый browser Origin без пути; по умолчанию `http://127.0.0.1:8080` |
| `HTTP_ADDR` | Auth | По умолчанию `127.0.0.1:8080` |
| `USER_SERVICE_ADDR` | Auth | По умолчанию `127.0.0.1:50051` |
| `JOB_SERVICE_ADDR` | Auth | По умолчанию `127.0.0.1:50052` |
| `DATABASE_URL` | User | Обязательное подключение PostgreSQL; не логировать |
| `GRPC_ADDR` | User | По умолчанию `127.0.0.1:50051` |
| `DATABASE_URL` | Job | Обязательное подключение PostgreSQL; не логировать |
| `GRPC_ADDR` | Job | По умолчанию `127.0.0.1:50052` |
| `DATABASE_URL` | Task | Обязательное подключение PostgreSQL; не логировать |
| `GRPC_ADDR` | Task | По умолчанию `127.0.0.1:50053` |

User применяет встроенные миграции sqlx перед открытием gRPC; Job и Task —
тот же idempotent-список, что и Auth. При добавлении
данных/реплик понадобится отдельная процедура развёртывания миграций; миграции
не редактируются задним числом. Существующая первая миграция сохранена.
Runtime-запросы SQLx параметризованы; сборка и unit-тесты не требуют БД.
В Compose для SQL настроен `statement_timeout=3000`; для ручного запуска
применить такой же лимит на уровне роли/подключения.

Auth `/healthz` проверяет HTTP-процесс. `/readyz` запрашивает стандартный gRPC
health API User, который обновляет статус на основе `SELECT 1` раз в секунду.
Поэтому обнаружение отказа БД не мгновенное. Процесс не перезапускается только
потому, что временно недоступна зависимость.

## Проверки без контейнеров

Требуются Go 1.25+, Rust 1.96+, `protoc`, C toolchain. Для генерации Go-контрактов
также нужны `curl` и `unzip`; закреплённые инструменты скачиваются в `.tools/`.

```sh
make proto
make test
```

`make proto` запускается из корня и использует единственный источник
`contracts/user.proto`. Rust генерирует код из того же файла при сборке.
Изменение расположения `.proto` меняет descriptor filename, но не имена RPC и
номера существующих полей.

CI проверяет работающие сервисы, generated Go-код и контейнерную smoke-проверку.
Пустые сервисы не выдаются за протестированные реализации. Проверки совместимости
с предыдущим опубликованным контрактом появятся до первого внешнего потребителя.

## Восстановление и эксплуатация

- **Ротация `JWT_SECRET`.** Access-cookie мгновенно становится невалидным
  (ресурсные запросы отвечают 401). Refresh-токен от ключа не зависит, поэтому
  сессия восстанавливается через `/refresh` без повторного входа. Менять секрет
  одновременно с перезапуском Auth.
- **Потеря volume `auth-db`.** Аккаунты, сессии и audit_log утрачены; профили
  в `user-db` остаются, но новая регистрация получает новый `user_id`, поэтому
  старые профили становятся сиротами. Восстановление — только из backup;
  без backup сирот удаляют в `user-db` по списку `user_id`, выгруженному из
  последнего снимка `auth-db` (базы раздельные, JOIN между ними невозможен).
- **Потеря volume `user-db`.** Профили утрачены, аккаунты целы; `GET /users/:id`
  отвечает 404, повторная доставка не сработает — `pending_profiles` уже пуст.
  Восстановление — только из backup либо ручная вставка профилей.
- **Зависшие `pending_profiles`.** Воркер делает до 20 попыток с интервалом
  30 секунд, затем перестаёт выбирать строку и пишет в лог
  `profile delivery abandoned`. После устранения причины вернуть попытку:
  `UPDATE pending_profiles SET attempts = 0 WHERE account_id = '<uuid>'` —
  строка уйдёт в ближайший тик. Если `last_error` = `username conflict`,
  возврат попытки бессмыслен: имя занято, username в строке нужно исправить
  или удалить строку.
- **Недоступный user-service.** `POST /register` отвечает 503/504, аккаунт
  сохраняется, профиль доставит retry-воркер после восстановления.
  `GET /users/:id` отвечает 503. Вмешательства не требуется.

## Ограничения текущей реализации

- gRPC между Auth и каталогами/User идёт по plaintext без сервисной
  аутентификации; допустимо только в изолированной локальной сети,
  mTLS/service identity — до публичного доступа (S6/S7).
- Rate limiting работает в пределах одного экземпляра Auth; между репликами
  лимиты не синхронизированы (распределённый лимитер — S4/S7).
- Публикация вакансий/заказов и отклики требуют подтверждённый email
  (S2, решение 4); остальные операции подтверждения не требуют.
- Публичный профиль содержит только `name`/`username`; контакт кандидата
  переносится откликом и виден только автору вакансии (S2). Управление
  видимостью прочих данных профиля — за пределами S2 (`product.md`).
- Совместимого rollout ключей JWT нет: смена `JWT_SECRET` инвалидирует
  access-cookie немедленно (сессия восстанавливается через `/refresh`).
- Метрики, трассировка, алерты и автоматические backups отсутствуют (S7);
  процедуры восстановления здесь ручные.
- Юнит-тесты сервисов не имеют тестовой БД: ветки `db == nil` в auth-service
  и SQL-поведение каталогов покрыты smoke на живой PostgreSQL, а не
  изолированными тестами. Снятие — в S7, перед нагрузочными и отказными
  испытаниями, где тестовая БД понадобится в любом случае.
- `mapDBError` каталогов распознаёт недоступность БД по подстрокам текста
  ошибки pgx; непокрытые формулировки сетевого сбоя уходят в 500 вместо
  503. Митигация: `statement_timeout` и клиентский deadline; типизированный
  разбор (`pgconn.ConnectError`, `net.OpError`) — вместе с тестовой БД.

Публичный доступ до закрытия этих пунктов запрещён. Текущий этап — S3 из
[плана](roadmap.md) (найм и выполнение заказа, решения — docs/s3-hiring.md).
