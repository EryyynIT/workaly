# Журнал реализации

## 2026-10-27 — S0: основание продукта и локального окружения

### Решения

- Продукт для реальных пользователей с равными условиями сторон.
- Вакансии и фриланс-заказы планируются одновременно, с разными моделями и API.
- Принципы продукта закреплены в `product.md`; детали споров, сроков и расчётов
  остаются предложениями до отдельного согласования.

### Изменения

- Описание продукта, границы сервисов, этапы S0–S7 и инструкция разработки.
- Единый `contracts/user.proto`, генерация Go-кода закреплёнными инструментами,
  Rust-сборка из того же источника. Стабильный user ID в ответах и JWT subject.
- Конфигурация вместо зашитых адресов; обязательный ключ JWT; согласованный TTL;
  HttpOnly/SameSite; базовая политика Origin и JSON-only запросы.
- Безопасное отображение gRPC-ошибок в HTTP, deadline от клиентского запроса,
  ограничение тела запроса и стоимости параллельной обработки паролей.
- User собирается без БД; runtime-запросы параметризованы, миграции встроены.
  Argon2 вынесен из async worker; неизвестный аккаунт тоже проходит проверку хеша.
- Liveness/readiness, JSON-логи и обработка SIGINT/SIGTERM.
- Compose, Dockerfile обоих работающих сервисов, unit-тесты, smoke и CI.
- Go module paths Auth и Task приведены к текущим именам сервисов в репозитории.
- Compose запускает образы `localhost/workaly-auth:s0` и `localhost/workaly-user:s0`.
- Некорректный UTF-8 и непарные Unicode-surrogate в JSON отклоняются до разбора:
  пароль больше не может молча измениться символом замены.
- Таймаут запроса PostgreSQL (`statement_timeout`) передаётся как HTTP 504,
  а не 500.

### Подтверждено локально

- Go: `go test -race`, `go vet`.
- Rust: unit-тесты, `cargo clippy --all-targets -- -D warnings`, сборка.
- Повторная генерация protobuf даёт те же Go-файлы.
- HTTP Auth → gRPC User → PostgreSQL 17 в контейнере: регистрация, повтор
  username, вход, одинаковый ответ для неизвестного пользователя и неверного пароля.
- Остановка PostgreSQL: readiness 503, liveness 200, безопасный 503 при входе;
  после запуска БД регистрация и вход снова работают.
- Синтаксис Compose проверен через `podman-compose config`.
- Повторные JSON-документы, управляющие символы и превышение лимита тела
  запроса отклоняются; секретные headers не выводятся стандартным panic recovery.
- Полная сборка образов и запуск через Compose подтверждены: регистрация, вход,
  дубликат, отказ PostgreSQL и восстановление.
- Некорректный UTF-8 и одиночный surrogate `\ud800` в пароле отклоняются с 400;
  валидная суррогатная пара принимается.
- Блокировка таблицы `users`: запрос отменяется `statement_timeout`,
  клиент получает HTTP 504 примерно через 3 секунды.

### Незавершённое

- ~~GitHub Actions добавлен, но удалённый запуск не выполнялся.~~ Выполнен:
  см. раздел «CI» ниже (run №1, все jobs зелёные).
- S0 не означает готовность к публичному доступу: ограничения безопасности
  перечислены в `development.md`. Нужны S1 и согласование открытых правил.

### Следующее изменение

S1: threat model и перенос credentials в Auth; модель отзывных сессий,
стабильная идентичность, восстановление доступа, защита от перебора и границы
видимости профиля. Не добавлять бизнес-API, доверяющее непроверенному user ID.

## 2026-10-27 — S1.1–S1.5: идентификация, сессии и перенос credentials

### Решения

- Идентификатор входа — email с подтверждением; username — публичное имя.
- Стабильный идентификатор аккаунта — UUID, назначаемый Auth при регистрации.
- Сессии: access JWT 15 мин, refresh 30 дней с ротацией; в БД — только хеши.
- Организации отложены; первая версия — только личные аккаунты.
- Доставка писем — абстракция; локально токены пишутся в лог при DEV_MAIL_LOG=true.
- Решения и модель угроз зафиксированы в `docs/s1-identity.md`.

### Изменения

- `contracts/user.proto` переписан: User теперь владеет только профилями
  (`CreateProfile` идемпотентен по `user_id`, `GetProfile`); Login/Register убраны.
- user-service: таблица `profiles(user_id UUID PK, name, username UNIQUE)`,
  аргон2 и проверка паролей удалены; новые unit-тесты.
- auth-service: собственная PostgreSQL (`auth-db`), таблицы `accounts`,
  `sessions`, `pending_profiles`, `action_tokens`, `audit_log`.
- Регистрация: аккаунт + задание на профиль в одной транзакции, синхронная
  идемпотентная доставка профиля в User.
- Вход по email+пароль (Argon2id), одинаковый ответ для неверного пароля и
  неизвестного email, dummy-hash для выравнивания таймингов.
- Refresh-rotation с обнаружением повторного использования (отзыв всех сессий),
  `/logout`, `/forgot-password` (одинаковый ответ), `/reset-password`
  (одноразовый токен, отзыв всех сессий).
- Rate limiting: регистрация 3/мин, вход 5/мин, восстановление 3/час (per email).
- Smoke расширен: refresh-rotation, отзыв старого токена, logout.

### Подтверждено локально

- Go: `go test -race`, `go vet`, `gofmt` — чисто (гонка в тестовом double устранена).
- Rust: 7 тестов, clippy — чисто.
- Compose с двумя БД поднимается; полный smoke проходит.
- Отказ auth-db: readiness 503, login 503; после восстановления — работает.
- Невалидный UTF-8 и непарный surrogate в пароле — 400; валидная пара — 200.
- Refresh: ротация выдаёт новый токен, старый — 401, logout отзывает сессию.

### Незавершённое

- Распределённый rate limiting (между несколькими экземплярами auth-service)
  не реализован — текущий лимитер per-process; требует Redis или аналога (S4/S7).
- Блокировка действий для неподтверждённых email не реализована: верификация
  работает, но не влияет на права (бизнес-правило для S2).
- Миграция данных существующих пользователей из старой таблицы `users`
  user-service не выполнялась (старые аккаунты S0 не перенесены; формат хешей
  изменён на PHC, поэтому следующая смена параметров не потребует миграции).

### CI

- 2026-10-27: первый прогон GitHub Actions (run №1 на `a509bd7`) зелёный по всем
  четырём jobs: Go (gofmt/vet/test -race), Rust (fmt/test/clippy), генерация
  контрактов без расхождений, compose-стенд со smoke и сценарием отказа auth-db.

### Исправлено в S1.6

- **Утечка деталей gRPC-ошибок в БД**: в `pending_profiles.last_error` теперь
  сохраняется только код ошибки (`Unavailable`, `DeadlineExceeded`), а не
  `err.Error()`, который мог содержать внутренние адреса и детали SQL.
- **`rows.Err()` не проверялся**: после циклов чтения добавлена проверка —
  обрыв сети посреди итерации больше не превращает неполный список сессий
  в успешный ответ.
- **Строковый разбор SQLSTATE заменён на pgconn**: `isDuplicateKey` и
  `writeDBError` используют `errors.As` с `*pgconn.PgError` (SQLSTATE 23505/57014).
  Дополнительно клиентский дедлайн запроса (`context.DeadlineExceeded`) маппится
  в 504, а ошибка установки соединения (в т.ч. таймаут dial) — в безопасный 503:
  порядок проверок важен, покрыто тестом.
- **Retry worker переведён на транзакцию**: `SELECT ... FOR UPDATE SKIP LOCKED`
  теперь держит блокировку строк на весь проход (раньше строки освобождались
  сразу после чтения — SKIP LOCKED был декоративным). Ряды с
  `attempts >= retryMaxAttempts` исключаются из выборки, «abandoned» пишется
  один раз; ошибки удаления/обновления строки логируются.
- **Тест на отмену контекста был пустым**: он отправлял запрос на `/login`,
  который вообще не вызывает gRPC. Переведён на `/register` (единственный
  handler с RPC) с проверкой, что фейк реально вызван.
- **Мёртвый код**: удалены `applicationDB`, `accountIDIfValid`, `deliverProfileAsync`.
- **Account enumeration**: регистрация на существующий email возвращает `200
  "if the email is not registered, a verification link has been sent"` без
  подтверждения существования аккаунта. Раньше было `409 "account already exists"`.
- **Конфликт username**: теперь различается от конфликта email. Конфликт email → 200
  (anti-enumeration), конфликт username → `409 "username already exists"`.
- **Аккаунт без профиля**: добавлен фоновый worker (`retry.go`), который каждые
  30 секунд повторяет доставку `pending_profiles`. При недоступности user-service
  регистрация возвращает 504, аккаунт сохраняется, профиль доставляется после
  восстановления. Проверено: профиль появился после перезапуска user-service.
- **Email не подтверждался**: добавлен `POST /verify-email`; токен одноразовый,
  после применения `email_verified_at` заполняется. Повторное использование → 401.
- **Утечка памяти в rate limiter**: ключи с протухшими записями вычищаются
  при росте map свыше 4096.
- **Формат хешей**: перешли на PHC-строки (`$argon2id$v=19$m=...,t=...,p=...$salt$hash`).
  Параметры хранятся внутри хеша; их можно менять без миграции данных.
  Go и Rust библиотеки читают один формат.
- **Повторная отправка verify-письма**: ограничена 1 раз в час на аккаунт.
- **Список сессий**: `GET /sessions` возвращает активные сессии аккаунта;
  `POST /logout-all` отзывает все refresh-токены. Проверено: после logout-all
  refresh даёт 401.

### Исправлено по итогам ревью 3

- **Обнаружение повтора refresh-токена не работало вовсе**: проверка сидела в
  недостижимой ветке «токен не найден» (хеш любого токена всегда есть в
  `refresh_token_hash` его строки). Повтор ротированного токена давал 401, но
  цепочку не отзывал, хотя docs/s1-identity.md обещала это свойство. Теперь
  при повторе отозванной и заменённой (`replaced_by`) сессии отзываются все
  сессии аккаунта; проверено вживую: после повтора старого токена текущий
  тоже даёт 401. В smoke добавлена проверка отзыва цепочки.
- **Гонка двойной ротации**: чтение сессии в `/refresh` шло без транзакции —
  два параллельных запроса с одним токеном создавали две живые сессии.
  Теперь чтение идёт с `FOR UPDATE` внутри транзакции ротации; проигравшая
  гонка сторона видит отозванную строку и запускает отзыв цепочки.
- **Регистрация с занятым username оставляла мёртвый аккаунт**: аккаунт
  коммитился, ответ был 409, профиль никогда не доставлялся, а тот же email
  нельзя было зарегистрировать заново с другим username. Теперь при
  `AlreadyExists` от user-service только что созданный аккаунт удаляется
  (каскадом чистится `pending_profiles`); повторная регистрация с новым
  username проходит полностью. Проверено вживую.
- **CI проверял отказ не той базы**: шаг останавливал `user-db`, а smoke ждёт
  503 от login, который зависит от `auth-db` — job падал бы на первом запуске.
  Исправлено на `stop auth-db`; сценарий прогнан локально.
- **Токен действия тратился до результата**: в `verify-email` и
  `reset-password` токен помечался использованным до обновления аккаунта;
  сбой между шагами оставлял «съеденный» токен без эффекта. Обе операции
  переведены в одну транзакцию.
- **`action_tokens` рос вечно**: использованные и истёкшие токены удаляются
  перед вставкой нового (`pruneUsedTokens`).
- **Удалён мёртвый `auth-service/migrations/0001_auth.sql`**: схему создаёт
  `migrate()` в db.go, файл ни на что не ссылался и уже разошёлся со схемой.
- **Немая потеря письма**: если вставка verify-токена не удалась, теперь
  пишется предупреждение, а не молчание.

### Следующее изменение

S1.9: публичный профиль в User, сквозная приёмка, документация по восстановлению.
