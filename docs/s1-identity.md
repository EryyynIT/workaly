# S1. Идентификация и безопасность — решения

Статус: согласовано с владельцем продукта (2026-10-27). Изменение решений
требует записи причины здесь и пересмотра затронутых контрактов.

## Принятые решения

1. **Идентификатор входа — email с подтверждением.** Email является логином
   и каналом восстановления. Username остаётся публичным изменяемым именем
   и не используется как ключ авторизации. Стабильный внутренний идентификатор
   — UUID аккаунта (`user_id`), одинаковый в Auth, User и будущих сервисах.
2. **Организации не входят в S1–S2.** Первая версия — только личные аккаунты.
   Модель организаций, членства и приглашений проектируется отдельным решением
   до появления бизнес-API, зависящих от неё.
3. **Доставка писем — абстракция отправителя.** На этом этапе реализация для
   локальной разработки пишет токен в лог и доступна только при явном
   `DEV_MAIL_LOG=true`. Реальный провайдер подключается конфигурацией без
   изменения кода. Письмо не содержит ничего, кроме ссылки/токена и срока действия.
4. **Сессии:** access JWT 15 минут, refresh-токен 30 дней с ротацией.
   В БД хранится только хеш refresh-токена. Повторное использование старого
   refresh-токена отзывает всю цепочку сессий. Отзыв refresh действует сразу;
   access-токен остаётся валидным до истечения (не более 15 минут) —
   операции, требующие немедленного отзыва, проверяют состояние сессии.
5. **Один аккаунт — любые роли по контексту действия.** Глобальных
   взаимоисключающих ролей («только заказчик» / «только исполнитель») нет.

## Модель угроз (S1)

| Угроза | Мера |
|---|---|
| Перебор пароля | Ограничение частоты попыток по аккаунту и источнику; ограничение стоимости хеширования; одинаковый ответ для неверного пароля и неизвестного email |
| Перечисление аккаунтов | Одинаковые ответы на восстановление; вход не раскрывает существование email; подтверждение email не отклоняет повторную регистрацию существующего адреса ответом 409, а отправляет письмо существующему владельцу |
| Кража refresh-токена | Хранение хеша, ротация, обнаружение повторного использования с отзывом цепочки |
| Кража access-токена | Короткий срок жизни; привязка к issuer/audience; немедленный отзыв невозможен до истечения — задокументированный компромисс |
| Подмена user ID клиентом | Внутренние сервисы принимают идентичность только из проверенного токена через доверенный путь, не из тела запроса |
| Частичный отказ регистрации | Аккаунт и профиль создаются в одной транзакции Auth-стороны с последующей идемпотентной доставкой профиля в User |
| Plaintext внутренний транспорт | Только локальная разработка; mTLS/service identity обязательны до публичного доступа (S6/S7) |

## Схема доверия

- Браузер доверяет только HTTPS + cookie с политикой Origin/CSRF.
- Auth — единственный владелец паролей, сессий и токенов восстановления.
- User доверяет `user_id`, полученному от Auth по внутреннему каналу,
  только при условии, что канал аутентифицирует Auth (пока: изолированная сеть).
- Ни один сервис не принимает `user_id` из клиентского запроса как
  доказательство личности или основание авторизации. Единственное исключение —
  чтение публичного профиля (`GET /users/:user_id`, RPC `GetPublicProfile`):
  там `user_id` служит адресом публичной записи (имя, username), прав не даёт
  и на решения об авторизации не влияет.

## Открытые вопросы (не блокируют S1)

- Политика повторного ввода пароля для чувствительных операций (смена email,
  удаление аккаунта) — определить вместе с этими операциями.
- Требования к сложности пароля сверх минимальной длины — после анализа
  компромиссов удобства; проверка по словарю утечек не входит в S1.
