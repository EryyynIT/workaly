# S2. Каталоги вакансий и заказов — решения

Статус: согласовано с владельцем продукта (2026-10-28). Изменение решений
требует записи причины здесь и пересмотра затронутых контрактов.

## Принятые решения

1. **Два сервиса с отдельными БД.** `job-service` (вакансии) и `task-service`
   (фриланс-заказы) под заготовками каталогов, созданными в S0. Вариант одного
   общего каталог-сервиса отвергнут: домены расходятся уже в S3 (найм против
   сделки с подтверждённой версией условий), общая схема связала бы миграции
   двух разных автоматов состояний. Отказ и нагрузка одного каталога не
   влияют на другой.
2. **HTTP-грань — auth-service.** Cookie, CSRF, лимиты и маппинг ошибок
   остаются в единственной открытой HTTP-точке. Каталоги — gRPC-сервисы;
   идентичность они получают как `actor_user_id` из subject проверенного JWT
   по внутреннему каналу. Поля `actor` в клиентских телах не существует.
   Право на запись проверяет сервис-владелец данных, а не гейт.
3. **Контакты кандидата переносятся откликом.** Кандидат по желанию указывает
   один канал связи (`contact`) в самом отклике; видит его только автор
   вакансии. Публичный профиль остаётся `name`+`username`; каталог и публичные
   эндпоинты отклики и контакты не отдают. Отклик не делает закрытые сведения
   общедоступными (product.md, правило вакансий 2).
4. **Публикация и отклики требуют подтверждённый email.** Черновики доступны
   без подтверждения. Проверку выполняет Auth при проксировании мутаций:
   отказ 403 с кодом `email_not_verified`. Закрывает отложенное в S1 решение.
5. **Автомат публикации: draft → published → closed.** В S2 `closed`
   терминален; отклик по закрытой публикации не принимается, история
   сохраняется. Черновик виден только автору; чужой черновик на чтение и
   мутации — 404, существование не раскрывается. Редактирование `published`
   — только с optimistic-версией: несовпадение `version` → 409; смена условий
   отражается как `updated_at` + `version` в представлении; полный журнал
   изменений — S3/S4. Publish и close выполняются CAS-переключением статуса.
6. **Один активный отклик на публикацию.** Частичный уникальный индекс
   `(публикация, аккаунт) WHERE status = 'active'`. Отзыв — мягкий
   (`status = 'withdrawn'`, `withdrawn_at`); после отзыва откликнуться можно
   снова, история строк сохраняется. Автор не может откликнуться на свою
   вакансию или предложить по своему заказу.

## Модели данных

Каждый сервис применяет собственный список idempotent-миграций — тот же
механизм, что в auth-service; миграции не редактируются задним числом.

`job-db`:

- `vacancies` — `id` UUID, `author_user_id` UUID (без FK: данные аккаунта в
  другой БД), `title` ≤ 120, `description` ≤ 5000, `employment_type`
  (`full_time`/`part_time`/`contract`/`internship`), `work_format`
  (`onsite`/`remote`/`hybrid`), `location` (опционально), `salary_min`/
  `salary_max` NUMERIC(12,2) (опционально, min ≤ max), `currency` CHAR(3)
  (обязательна при любой зарплате), `status`, `version` > 0, временные метки
  `created_at`/`updated_at`/`published_at`/`closed_at`.
- `vacancy_responses` — `vacancy_id` FK, `candidate_user_id`, `cover_letter`
  ≤ 4000, `contact` (опционально, ≤ 200), `status`
  (`active`/`withdrawn`), `withdrawn_at` согласован со статусом.

Индексы: публичный каталог по `(published_at DESC, id) WHERE status =
'published'`; авторский список по `(author_user_id, created_at DESC)`; отклики
по публикации и по кандидату.

`task-db` (зеркально, под сделку S3):

- `orders` — вместо зарплатной вилки обязательный бюджет: `budget_type`
  (`fixed`/`hourly`), `budget_amount` NUMERIC(12,2) > 0, `currency` CHAR(3),
  `deadline` DATE (опционально).
- `order_proposals` — `order_id` FK, `executor_user_id`, `message` ≤ 4000,
  `proposed_amount` > 0, `currency`, `proposed_deadline` (опционально).
  Предложение — черновик будущих подтверждённых условий сделки (S3).

## Поверхность API

HTTP-грань (auth-service) → gRPC. Мутации требуют сессию; публикация,
отклики и предложения — подтверждённый email.

- Вакансии: `POST /vacancies`, `PATCH /vacancies/:id`, `POST
  /vacancies/:id/publish`, `POST /vacancies/:id/close`, `GET /vacancies`
  (публичный каталог), `GET /vacancies/:id` (публично, только published),
  `GET /my/vacancies` (все свои статусы), `POST /vacancies/:id/responses`,
  `GET /vacancies/:id/responses` (только автор), отзыв и чтение своего
  отклика.
- Заказы: зеркально `/orders` + `orders/:id/proposals`.
- Коды: 400 (валидация), 401 (нет сессии), 403 (email не подтверждён),
  404 (чужое или не существует), 409 (повторный отклик, конфликт версии),
  429 (лимиты), 503/504 (недоступность/deadline зависимости).

Пагинация каталога — keyset по `(published_at, id)`, лимит страницы ≤ 50;
фильтры первого набора: `employment_type`, `work_format`, бюджет, поиск по
заголовку (ILIKE).

## Модель угроз (S2)

| Угроза | Мера |
|---|---|
| Чужой доступ к черновику или откликам | Мутации и списки выполняются только с `actor_user_id` от Auth по внутреннему каналу; чужой ресурс — 404 |
| Утечка контактов | `contact` видит только автор вакансии; в каталог, публичные чтения и публичный профиль контакты не попадают |
| Гонка конкурентного редактирования | Optimistic `version` в UPDATE и CAS на смене статуса; несовпадение — 409 |
| Спам откликами | Один активный отклик на пару (публикация, аккаунт); лимит создания по IP на HTTP-грани |
| Публикация ботами | Publish, отклик и предложение требуют подтверждённый email |
| Подмена автора | `author_user_id` проставляется только из `actor_user_id`; из тела запроса автора не существует |

## Схема доверия (дополнение к S1)

- Auth аутентифицирует браузер (сессия) и транслирует subject проверенного
  JWT в `actor_user_id` внутреннего вызова gRPC.
- Job/Task проверяют право на действие по владельцу записи сами; гейт не
  принимает решений о владении.
- Никакая авторизация не строится на `user_id` из клиентского запроса —
  правило S1 действует и для каталогов.

## Открытые вопросы (не блокируют S2)

- Права автора-организации — отдельное решение до появления организаций
  (S1-решение 2 остаётся в силе).
- Полный журнал изменений существенных условий — S3 (подтверждённые версии
  условий Task) и S4 (события для Job).
- Полнотекстовый поиск по каталогам — после анализа нагрузки; в S2
  минимальные фильтры и ILIKE.
- Отображение имени автора в каталоге — фронтенд резолвит через публичный
  профиль; денормализации в БД каталогов нет.
