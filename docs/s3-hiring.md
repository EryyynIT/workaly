# S3. Найм и выполнение заказа — решения

Статус: согласовано с владельцем продукта (2026-10-30). Изменение решений
требует записи причины здесь и пересмотра затронутых контрактов.

## Принятые решения

1. **Job: полный оффер-цикл отклика.** Статусы `vacancy_responses.status`:
   `active` → `rejected` (работодатель, опциональная причина) |
   `offer_sent` (работодатель направляет предложение) → `offer_accepted`
   (кандидат) → `hired` (работодатель подтверждает выход) либо
   `offer_declined` (кандидат). `withdrawn` (отзыв кандидатом) возможен из
   любого нефинального состояния, кроме `hired`. Терминальные: `rejected`,
   `offer_declined`, `withdrawn`, `hired`. Фиктивной «приёмки работ» в найме
   нет (roadmap S3). Одновременно по вакансии существует не более одного
   отклика в `offer_sent`/`offer_accepted` (частичный уникальный индекс);
   `hired` не блокирует последующие предложения (массовый найм с одной
   вакансии возможен). `hired` не закрывает вакансию автоматически — закрытие
   остаётся решением автора. Закрытие вакансии отклоняет незавершённые
   предложения: `offer_sent`/`offer_accepted` → `rejected` с системной
   причиной `vacancy_closed` в той же транзакции, что и CAS закрытия.
   Закрытая вакансия останавливает конвейер: переходы из `active` (отказ,
   оффер) требуют статуса вакансии `published` в гарде CAS; активные отклики
   закрытой вакансии остаются историей без дальнейших переходов, кроме
   отзыва кандидатом.
2. **Task: заказчик корректирует условия при выборе; handshake только при
   расхождении.** Выбор предложения создаёт сделку с неизменяемой версией
   условий v1 (сумма, валюта, срок, число включённых доработок, критерии
   приёмки). Если условия совпадают с предложением исполнителя — сделка
   стартует сразу (`in_progress`); если отличаются — исполнитель подтверждает
   или отклоняет (`terms_pending`); при отклонении выбор отменяется, заказ
   возвращается к списку предложений, а временная сделка удаляется: она не
   фиксирует согласованные условия, и тот же заказ должен допускать новый выбор.
   Ответ `declined` возвращается вызывающей стороне, но не становится исторической
   сделкой. Изменение согласованных условий
   (версии v2+) в объём S3 не входит — отдельный инкремент после основного
   автомата (правило 2 product.md остаётся целевым требованием, старые
   версии будут сохраняться).
3. **Task: отмена до сдачи, причина обязательна.** Закрытие заказа
   (`closed`) возможно до выбора исполнителя (из `draft`/`published` — как в
   S2). После старта сделки заказ не закрывается: только отмена
   (`cancelled`) инициатором-заказчиком с обязательной причиной, возможна до
   первой сдачи (`in_progress`, `revision_requested`). Терминальные статусы
   сделки: `completed`, `cancelled`.
4. **Task: таймеры молчания с автоматическими действиями.** Планировщик
   таймеров в task-service. Авто-приёмка сдачи через 3 дня молчания
   заказчика (`submitted` → `completed`); авто-возврат в работу при 7 днях
   молчания исполнителя на запрос доработки (`revision_requested` →
   `in_progress`). Сроки — константы конфигурации сервиса, не захардкожены в
   SQL. «Неопределённый результат команды» (roadmap S3): автоматические
   переходы идемпотентны — таймер повторяет CAS до успеха, дубль перехода
   безопасен.

## Автоматы состояний

### Отклик на вакансию (Job)

```
active ──reject(автор, причина?)──────────────▶ rejected        (терминал)
active ──send_offer(автор)────────────────────▶ offer_sent
offer_sent ──accept(кандидат)─────────────────▶ offer_accepted
offer_sent ──decline(кандидат, причина?)──────▶ offer_declined  (терминал)
offer_sent ──withdraw_offer(автор)────────────▶ active          (возврат)
offer_accepted ──mark_hired(автор)────────────▶ hired           (терминал)
любое нефинальное, кроме hired ──withdraw(кандидат)▶ withdrawn  (терминал)
закрытие вакансии: offer_sent/offer_accepted ─▶ rejected (причина vacancy_closed)
```

Ограничение: не более одного отклика в `offer_sent`/`offer_accepted` на
вакансию (частичный уникальный индекс). Кандидат видит статус своего отклика;
автор видит статусы всех откликов своей вакансии; причины отказа видны только
адресату (кандидату для reject/decline-а — соответственно сторонам: причина
reject видна кандидату, причина decline видна автору).

### Сделка по заказу (Task) — инкремент S3.2

```
order: draft ─publish─▶ published ─close─▶ closed   (как в S2, до выбора исполнителя)
published ─select(заказчик, условия = предложению)─▶ deal: in_progress
published ─select(заказчик, условия ≠ предложению)─▶ deal: terms_pending
terms_pending ─confirm(исполнитель)─▶ in_progress
terms_pending ─decline(исполнитель)─▶ выбор отменён, order снова published
in_progress ─submit(исполнитель, результат)─▶ submitted
submitted ─accept(заказчик)─▶ completed            (терминал)
submitted ─request_revision(заказчик, причина)─▶ revision_requested
revision_requested ─submit(исполнитель)─▶ submitted  (новая итерация сдачи)
in_progress/revision_requested ─cancel(заказчик, причина обязательна)─▶ cancelled (терминал)
submitted, 3 дня молчания заказчика ─таймер─▶ completed (авто-приёмка)
revision_requested, 7 дней молчания исполнителя ─таймер─▶ in_progress
```

Число доработок из условий v1 — лимит переходов `submitted →
revision_requested`; исчерпание лимита не блокирует приёмку/отмену, запрос
доработки сверх лимита отклоняется (FailedPrecondition). Итерации сдачи
сохраняются (результат, метка времени и уникальный в рамках сделки ключ
идемпотентности); клиент повторяет запрос с тем же ключом при неопределённом
ответе. Повтор возвращает исходную итерацию независимо от текущего статуса
сделки; повторное использование ключа с другим содержимым отклоняется. Старые
сдачи до миграции имеют `NULL`-ключи и не могут быть восстановлены этим
механизмом.

## Модель угроз (дополнение к S2)

| Угроза | Мера |
|---|---|
| Двойной оффер по одной вакансии (гонка) | Частичный уникальный индекс; гонка → 409 |
| Подмена стороны решения | Все переходы принимают `actor_user_id` только из JWT по внутреннему каналу; сторона проверяется по владению записью в сервисе |
| Запрещённый переход | CAS по ожидаемому статусу; несовпадение → 409 (не раскрывая текущее состояние чужой записи — чужой ресурс остаётся 404) |
| Бесконечное молчание стороны | Таймеры S3.4 с идемпотентными CAS-переходами |
| Потеря истории решений | Статусы и причины — столбцы записей; мягкие переходы, удаления нет |

## Открытые вопросы (не блокируют S3)

- Общение по отклику/сделке (чат) — S4; до него стороны видят статусы и
  причины, переписка вне системы.
- Конкретные сроки таймеров (3/7 дней) — начальные константы; пересмотр по
  метрикам до S7.
- Отказ кандидата от уже принятого оффера (`offer_accepted` → ?) — в S3
  отзыв кандидатом из `offer_accepted` переводит в `withdrawn`; отдельного
  статуса «сорвал выход» нет.
- Уведомления сторон о переходах — S4; до них сторона узнаёт о смене статуса
  по запросу своих списков.
